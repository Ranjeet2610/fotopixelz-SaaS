# QA

## Purpose
The `QAReview` Prisma model and `qa` API module suggest a per-asset QA review-record system, distinct from the order-level QA workflow that actually runs today.

## Users / Roles
Not established — no working code exists to determine actual role interaction beyond the model's `reviewerId` field.

## Current Implementation
**Scaffolding exists but production workflow is not implemented.** `services/api/src/modules/qa/qa.service.ts` contains exactly one function: `getQaStatus()` returning `{ module: 'qa', status: 'placeholder' }`. `qa.routes.ts` exposes only `GET /qa/health`.

## Frontend
`apps/admin/src/app/admin/qa/page.tsx` and `apps/admin/src/components/qa-review-panel.tsx` exist and present a QA queue/review UI, but — based on the confirmed order-level QA transition logic in `docs/08-ORDERS.md` — the actual review action is expected to go through `orders` (`PATCH /orders/status` with QA role, or `POST /orders/request-revision`), not the `qa` module's endpoints (which don't exist beyond health). This frontend-to-backend wiring was not independently re-verified line-by-line in this pass; it is flagged here as the most likely explanation given the confirmed backend reality.

## Backend
`services/api/src/modules/qa/` — controller/routes/service (placeholder)/types/validator files present but unused beyond the health check.

## Database
`QAReview` model exists (`assetId`, `reviewerId`, `status` enum `PENDING/IN_REVIEW/PASSED/FAILED`, `comments`) but is **not written to or read from** in the traced `orders.service.ts`/`assets.service.ts` code. The real QA outcome is represented via `Order.status` (`READY_FOR_QA`/`DELIVERED`/`REVISION_REQUIRED`) plus `Asset.qaNotes` (a JSON field on `Asset`, not a `QAReview` row).

## APIs
Only `GET /qa/health`.

## Workflow
